# План развития продукта BG Foot

## 1. Цель

Довести BG Foot от функциональной системы ведения соревнований до удобного
сайта для болельщиков, представителей команд, рефери и организаторов.

Основной спортивный контур уже существует: сезоны, Чемпионаты и Кубки, команды,
игроки, туры, матчи, протоколы, заявки, трансферы, дисциплина, уведомления,
регламенты и Зал славы. Следующие работы должны улучшать ежедневные сценарии,
снижать ручную работу организаторов и давать смысл регистрации обычного
пользователя.

## 2. Правила выполнения

1. Работаем последовательно по этапам этого плана.
2. Новый этап начинаем после завершения и проверки предыдущего.
3. Изменения БД оформляем только новой Flyway migration.
4. Backend, frontend и mailer меняем вместе, когда функция затрагивает их.
5. Добавляем только тесты, которые проверяют важное поведение.
6. После крупного этапа обновляем RELEASE.md и связанную документацию.
7. Перед переносом dev → test выполняем полный штатный набор проверок.
8. Новую настройку добавляем только для данных, которые будут менять.
9. Не создаём сервисы и архитектурные слои без продуктовой необходимости.

### Этап 0. Реальная привязка пользователя к команде

**Приоритет:** P0
**Зависимости:** нет
**Статус:** выполнен 12.09.2026

Сейчас frontend может подставить вымышленное название команды, если backend не
вернул реальную область доступа.

#### Фактический результат

- удалён подбор вымышленной команды по email и ID пользователя;
- данные команды и полномочия берутся только из teamScopes backend;
- некорректные team scope отбрасываются;
- представитель без команды не проходит в командный кабинет;
- трансферы требуют canEditApplication, управление игроками — canEditRoster;
- добавлены проверки нормализации доступа и route guard;
- пройдены 93 frontend-теста, ESLint и production build.

#### Что делаем

1. Удаляем TEAM_POOL, хэширование пользователя и подбор команды из auth.js.
2. Используем только сведения из /api/admin/access/me.
3. Показываем «Команда не назначена», если активной привязки нет.
4. Не открываем заявки и трансферы без реального teamId.
5. Проверяем пользователя без команды и представителя с назначенной командой.

#### Готово, когда

Интерфейс никогда не показывает команду, которой нет в правах пользователя.

- публичный экран туров на маршруте `/` визуально не изменялся по решению владельца продукта;

#### Что делаем

3. Для переноса храним новое время и причину.
4. Не считаем отменённый матч в таблице и статистике.
5. Для технического результата явно показываем основание.
6. Уведомляем представителей и подписанных болельщиков о переносе и отмене.
7. Показываем статус в календаре, турах, профиле команды и матче.

#### Готово, когда

### Этап 11. Журнал критических действий

**Статус:** выполнен, 13.09.2026.

Добавлены неизменяемый журнал, автор и время, разрешённые снимки до/после.
Записи сохраняются в той же транзакции, что бизнес-изменение. Покрыты
подтверждение/открытие/правка протокола и его событий, расписание и удаление
матча, публикация тура, создание и решения по трансферу, решения по заявке,
назначение/отзыв ролей и доступа к команде, регламенты, дисциплинарные

деактивированных объектов сохраняется снимок; доступные объекты имеют
переход, деактивированные — переход в административный раздел.
Журнал ведётся для новых действий, прошлые операции не реконструируются.
Пароли, токены и данные файлов не входят в список разрешённых полей.


**Приоритет:** P1
**Зависимости:** можно делать вместе с этапом 10

   трансфер, решение по заявке, назначение прав, изменение регламента,
   дисциплины и деактивацию сущности.
3. Храним тип сущности, ID, действие, автора, время и безопасный снимок
   изменённых полей.
4. Не сохраняем пароли, токены и бинарные файлы.

#### Frontend

1. Добавляем журнал в админку.
2. Фильтруем по периоду, пользователю, сущности и действию.
