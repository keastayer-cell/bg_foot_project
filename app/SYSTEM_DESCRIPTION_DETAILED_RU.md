# Подробное описание системы статистики футбола

## 1. Назначение системы

Система предназначена для ведения любительского футбольного турнира и состоит из трех связанных компонентов:

1. `app` — backend на Spring Boot.
2. `web` — frontend на Vue 3.
3. `db` — база данных PostgreSQL со схемой `work`, управляемая через Flyway-миграции.

На практике система решает сразу несколько задач:

- авторизация пользователей;
- разграничение ролей и прав доступа;
- управление сезонами;
- привязка команд к сезонам;
- автоматическое формирование структуры регулярного чемпионата;
- управление турами и матчами;
- публикация туров для публичного сайта;
- хранение и редактирование реального протокола матча;
- хранение составов команд на матч;
- сезонная заявка игроков;
- отдельный кабинет представителя команды.

Система строится как единый продукт, но логически разделена на 3 уровня:

- `web` отвечает за интерфейс и пользовательские действия;
- `app` отвечает за бизнес-логику, валидацию, безопасность и API;
- `db` отвечает за постоянное хранение данных, истории и ограничений.

## 2. Общая архитектурная схема

Общий поток работы системы выглядит так:

1. Пользователь открывает frontend.
2. Frontend либо работает как гость, либо авторизует пользователя через backend.
3. Frontend вызывает backend API по HTTP.
4. Backend проверяет JWT, роль и data-level ограничения.
5. Backend читает или изменяет данные в PostgreSQL.
6. Backend возвращает JSON.
7. Frontend отображает результат в соответствующем разделе.

Технически это выглядит так:

- браузер пользователя работает с `football-stats-web`;
- frontend отправляет запросы на `http://127.0.0.1:8080/api/...`;
- backend `football-stats-app` работает с PostgreSQL `football_db`;
- структура БД и ее эволюция описаны миграциями в `src/main/resources/db/migration`.

## 3. Компонент 1: Backend (`football-stats-app`)

### 3.1. Технологический стек

Backend построен на:

- Java 21;
- Spring Boot;
- Spring Web;
- Spring Data JPA;
- Spring Security;
- JWT-аутентификации;
- Flyway;
- PostgreSQL.

Основная задача backend — быть единственным источником истины для бизнес-правил.

Во frontend не должно быть логики, которая решает, можно или нельзя менять данные. Frontend только подготавливает запрос и показывает ответ. Все ключевые проверки выполняются в backend.

### 3.2. Структура backend-проекта

Основной пакет:

- `src/main/java/com/footballstats/backend`

Ключевые подпакеты:

- `config` — конфигурация Spring и security;
- `controller` — REST API слой;
- `domain` — JPA-сущности;
- `dto` — вспомогательные DTO;
- `repository` — доступ к БД;
- `security` — JWT и фильтры доступа;
- `service` — бизнес-логика;
- `health` — служебные health endpoints.

### 3.3. Роль каждого backend-слоя

#### Controller

Контроллеры принимают HTTP-запросы, читают path/query/body-параметры и передают вызов в сервисы.

Основные контроллеры:

- `AuthController` — регистрация, логин, guest login, текущий пользователь;
- `AdminAccessController` — управление ролями и привязками представителей;
- `SeasonController` — сезоны и команды сезона;
- `TourController` — туры и матчи тура;
- `TeamController` — команды и игроки команды;
- `PlayerController` — игроки и карточка игрока;
- `MatchController` — матч, протокол, составы на матч;
- `TeamRepController` — кабинет представителя команды.

#### Service

Сервисы содержат реальные бизнес-правила.

Именно здесь принимаются решения вида:

- можно ли команде участвовать в сезоне;
- можно ли менять структуру сезона;
- можно ли представителю менять конкретную команду;
- можно ли добавить игрока в заявку сезона;
- можно ли включить игрока в состав на матч;
- можно ли игроку быть в сезоне за другую команду.

#### Repository

Репозитории работают с JPA и SQL-подобными выборками.

Они отвечают за:

- поиск сущностей;
- фильтрацию активных записей;
- `JOIN FETCH` там, где без этого возможны lazy-loading ошибки;
- выборки для экранов frontend.

#### Domain

Сущности отражают таблицы БД.

Например:

- `Season` — сезон;
- `Team` — команда;
- `Player` — игрок;
- `SeasonTeam` — участие команды в сезоне;
- `PlayerTeam` — связь игрока с командой;
- `Tour` — тур;
- `TourMatch` — матч;
- `MatchProtocol` — протокол матча;
- `MatchEvent` — событие матча;
- `MatchLineup` — заявка команды на матч;
- `MatchLineupPlayer` — игрок в матчевой заявке;
- `SeasonPlayer` — игрок, заявленный на конкретный сезон за конкретную команду;
- `UserTeamScope` — data-level привязка пользователя к команде.

### 3.4. Безопасность и доступ

Backend использует два независимых уровня доступа.

#### Уровень 1. API-level access

Определяет, кто вообще может вызвать endpoint.

Хранится в таблице:

- `work.w_api_access_rule`

Проверяется через:

- `ApiAccessRuleFilter`
- `ApiAccessRuleService`

Логика такая:

- endpoint может быть разрешен для роли;
- если роль не имеет права на URL и HTTP method, запрос блокируется еще до бизнес-логики.

#### Уровень 2. Data-level access

Определяет, какими именно данными пользователь может управлять.

Для представителей это хранится в:

- `work.w_user_team_scope`

То есть представитель команды может иметь право вызывать нужный API, но backend все равно дополнительно проверяет, что он работает только со своей командой.

Это принципиально важно: API-level и data-level — разные механизмы.

#### Роли

Система использует роли:

- `SUPER_ADMIN`;
- `USER`;
- `TEAM_REP`.

Правила по ролям:

- `SUPER_ADMIN` имеет code-level bypass и может управлять всей системой;
- `USER` в основном читает данные;
- `TEAM_REP` работает только в рамках своей команды и своих функций.

### 3.5. Аутентификация

Авторизация строится на JWT.

Основные endpoints:

- `POST /api/auth/register`
- `POST /api/auth/login`
- `POST /api/auth/guest`
- `GET /api/auth/me`

Общий сценарий:

1. Frontend отправляет логин/пароль.
2. Backend проверяет пользователя.
3. Backend возвращает JWT.
4. Frontend сохраняет токен в `sessionStorage`.
5. Дальше frontend отправляет `Authorization: Bearer <token>`.

### 3.6. Ключевые подсистемы backend

#### 3.6.1. Сезоны

Сезон — центральная сущность системы.

Он хранит:

- название;
- признак активности;
- аудит;
- формат проведения.

Важные поля сезона:

- `rounds_count` — число кругов регулярки;
- `playoff_enabled` — включен ли плей-офф;
- `playoff_team_count` — сколько команд выходит в плей-офф.

Сезон — это не просто справочник, а контейнер, внутри которого живут:

- участвующие команды;
- туры;
- матчи;
- сезонные заявки игроков.

#### 3.6.2. Команды сезона

Участие команды в сезоне хранится отдельно через `SeasonTeam`.

Это значит:

- одна команда может участвовать в нескольких сезонах;
- один сезон может содержать несколько команд;
- состав команд сезона не зашит в саму таблицу сезона.

#### 3.6.3. Туры и матчи

Backend хранит расписание отдельно от протокола.

Это правильная архитектурная развязка:

- `Tour` и `TourMatch` описывают структуру соревнования;
- `MatchProtocol` и `MatchEvent` описывают, что реально произошло в матче.

`Tour` хранит:

- сезон;
- тип стадии;
- номер раунда;
- порядок сортировки;
- дату;
- признак публикации.

`TourMatch` хранит:

- тур;
- домашнюю команду;
- гостевую команду;
- дату матча;
- активность.

#### 3.6.4. Публикация туров

Есть разделение между внутренними и публичными данными.

Логика такая:

- администратор может создавать туры и матчи;
- на публичную страницу попадают только опубликованные туры;
- для frontend сделан агрегирующий endpoint `GET /api/seasons/{seasonId}/overview`.

На текущем этапе этот endpoint возвращает уже не только туры, но и готовую турнирную таблицу сезона:

- `season`
- `teams`
- `tours`
- `standingsConfig`
- `standings`

Это уменьшает количество одинаковых запросов с frontend и делает загрузку страницы проще.

#### 3.6.4.1. Турнирная таблица сезона

Для таблицы сезона выделен отдельный слой хранения.

Используются таблицы:

- `w_season_standings_config`
- `w_season_standings_row`

Это означает следующее:

- frontend не пересчитывает таблицу из матчей на лету;
- backend не пересчитывает таблицу на каждом `GET`;
- при чтении сезона отдается уже сохраненный snapshot;
- пересчет выполняется backend-логикой при изменениях, влияющих на итоги;
- для ранее подтвержденных матчей снэпшот был заполнен отдельной backfill-миграцией.

#### 3.6.5. Протокол матча

Протокол матча хранится отдельно от расписания.

Структура:

- `MatchProtocol` — статус матча, счет, лучший игрок, технические поражения, заметки;
- `MatchEvent` — голы, карточки, замены и другие события.

Текущая модель редактирования уже не event-first, а lineup-first:

- супер-админ заполняет счет и статистику по игрокам прямо по заявкам матча;
- backend принимает `playerStats`;
- backend проверяет принадлежность игрока к заявке матча;
- backend проверяет совпадение суммы голов и счета;
- backend сам генерирует `MatchEvent` на основе сохраненной статистики.

Отдельно поддержаны технические поражения:

- `homeTechnicalDefeat`
- `awayTechnicalDefeat`

Если выставлено техническое поражение, счет принудительно становится `3:0` или `0:3`.

Это позволяет:

- открыть отдельную страницу матча;
- редактировать матч уже после создания;
- восстанавливать историю событий;
- показывать счет и статус в публичной части.

#### 3.6.6. Составы на матч

Для матчевых заявок введен отдельный слой:

- `MatchLineup` — заявка конкретной команды на конкретный матч;
- `MatchLineupPlayer` — конкретные игроки в заявке.

Правило допуска игрока в матчевую заявку жесткое:

игрок должен одновременно:

- быть в составе команды;
- быть заявлен на сезон матча именно за эту же команду.

То есть матчевая заявка не живет сама по себе. Она зависит от сезонной заявки.

#### 3.6.7. Сезонные заявки игроков

Это одна из главных текущих подсистем.

Раньше использовалось старое поле `w_player.season_id`, но от него ушли как от основного механизма.

Теперь используется таблица:

- `work.w_season_player`

Она хранит не абстрактную привязку игрока к сезону, а конкретную связь:

- игрок;
- сезон;
- команда;
- активность;
- аудит.

Текущая бизнес-логика здесь следующая:

- один игрок может участвовать в нескольких сезонах;
- один игрок может играть за разные команды в разных сезонах;
- один игрок не может одновременно быть заявлен в одном и том же сезоне за две команды;
- удаление из сезонной заявки не удаляет игрока из базы;
- сезонная история игрока хранится как отдельный слой данных.

Именно эта модель нужна для будущего нормального модуля трансферов, потому что она уже отделяет сезонную принадлежность от глобальной карточки игрока.

#### 3.6.8. Кабинет представителя команды

Для представителей реализован отдельный backend API.

Основные операции:

- получить сезоны своей команды;
- получить текущий состав своей команды;
- создать игрока;
- редактировать игрока;
- получить игроков по сезону;
- сохранить заявку сезона;
- точечно добавить игрока в сезон;
- убрать игрока из сезона.

Отдельно реализован сценарий выбора уже существующего игрока:

- frontend получает список игроков, которые свободны в выбранном сезоне;
- backend проверяет, что этот игрок не заявлен в том же сезоне за другую команду;
- после этого игрок добавляется в сезонную заявку команды представителя.

### 3.7. Ошибки и стабильность backend

В проекте уже учитывались реальные проблемы, которые обычно ломают такие системы:

- `LazyInitializationException` на сущностях с ленивыми связями;
- конфликт уникальности при повторном сохранении тех же команд сезона;
- лишние запросы frontend;
- расхождение между mock-UI и реальным backend.

Поэтому важные места уже усилены:

- некоторые выборки сделаны через `JOIN FETCH`;
- после массового удаления связей используется `flush()` там, где это критично;
- frontend переведен с локальных моков на реальные endpoints;
- агрегирующие endpoints добавлены там, где это снижает сложность UI.

## 4. Компонент 2: Frontend (`football-stats-web`)

### 4.1. Технологический стек

Frontend построен на:

- Vue 3;
- Vite;
- Vue Router;
- Composition API;
- обычном `fetch` для HTTP.

Задача frontend — быть тонким клиентом, который:

- показывает данные;
- хранит auth state;
- вызывает backend;
- управляет формами;
- отображает ошибки и успешные операции.

### 4.2. Структура frontend-проекта

Ключевые каталоги:

- `src/pages` — экраны приложения;
- `src/router` — маршруты;
- `src/store` — auth и часть клиентского состояния;
- `src/data` — каталог API Explorer и вспомогательные данные;
- `src/composables` — небольшие utility hooks;
- `src/style.css` — общие стили приложения.

### 4.3. Маршрутизация

Маршруты frontend:

- `/` — туры и публичная главная;
- `/players` — список игроков;
- `/teams` — список команд;
- `/create` — экран создания, требующий авторизации;
- `/admin` — админка, доступна только `SUPER_ADMIN`;
- `/team-rep-dashboard` — кабинет представителя, доступен только `TEAM_REP`;
- `/api-explorer` — просмотр API;
- `/api-explorer/test/:endpointKey` — тестирование endpoint;
- `/match/:id` — отдельная страница матча.

Route guard работает через `useAuth()`:

- если маршрут требует auth и пользователь не залогинен, происходит редирект на `/`;
- если маршрут требует `SUPER_ADMIN`, проверяется роль;
- если маршрут требует `TEAM_REP`, проверяется роль.

### 4.4. Авторизация во frontend

Auth logic живет в:

- `src/store/auth.js`

Что делает этот слой:

- хранит JWT и текущего пользователя;
- восстанавливает состояние из `sessionStorage`;
- делает `login`, `register`, `guestLogin`, `logout`;
- подставляет Bearer token;
- загружает `me` и `access/me`;
- вычисляет роли и команду пользователя.

Есть два режима сетевых запросов:

- `authorizedApiRequest` — когда токен обязателен;
- `optionalAuthApiRequest` — когда endpoint публичный, но токен можно отправить при наличии.

### 4.5. Страницы frontend

#### Tours.vue

Главная публичная страница.

Отвечает за:

- выбор сезона;
- загрузку overview сезона;
- отображение сохраненной турнирной таблицы слева;
- отображение опубликованных туров справа;
- раскрытие тура в список матчей;
- переход на страницу конкретного матча.

Блок команд сезона с главной страницы убран, чтобы не дублировать информацию и не перегружать стартовый экран.

#### Match.vue

Страница матча.

Показывает:

- команды;
- тур и сезон;
- статус;
- счет;
- заявки команд на матч;
- сохраненную статистику игроков;
- события протокола, уже построенные backend;
- домашнюю и гостевую заявку;
- режим редактирования для тех, кто имеет права.

Текущая страница матча построена по принципу lineups-first:

- сначала показываются составы;
- затем блок протокола;
- публичные пользователи видят readonly-данные;
- супер-админ может редактировать счет, статистику игроков и техническое поражение.

#### Players.vue

Экран игроков.

Использует backend-фильтры и позволяет смотреть игроков с учетом:

- имени;
- команды;
- сезона;
- статистики.

Сейчас на этом экране popup карточки игрока уже работает на реальных API, а не на хардкоде.

При открытии карточки frontend вызывает:

- `GET /api/players/{playerId}`
- `GET /api/players/{playerId}/history`

И показывает:

- фото игрока;
- текущую команду;
- дату рождения;
- город проживания;
- голы;
- желтые карточки;
- красные карточки;
- историю команд.

Popup намеренно увеличен по размеру, чтобы карточка выглядела как полноценный профиль игрока.

#### Teams.vue

Экран команд.

Показывает список команд и связанную информацию по ним.

#### Admin.vue

Главный административный экран.

Он уже содержит несколько больших разделов:

- управление сезонами;
- управление командами;
- управление турами;
- управление матчами внутри тура;
- управление игроками;
- управление ролями;
- управление представителями.

Именно этот экран является центром ручного администрирования системы.

#### TeamRepDashboard.vue

Личный кабинет представителя команды.

Сейчас он уже работает не через localStorage mocks, а через реальный backend API.

Что он показывает:

- профиль пользователя;
- его команду;
- сезоны команды;
- текущий состав команды;
- сезонную заявку выбранного сезона;
- список доступных игроков, которых можно добавить в сезон;
- формы создания и редактирования игрока.

#### ApiExplorer.vue и ApiExplorerTest.vue

Это встроенная документация и ручной тестер API.

Они полезны для:

- проверки endpoint-ов;
- отладки прав;
- демонстрации структуры API;
- ручных smoke-тестов без Postman.

### 4.6. Особенность frontend-состояния

В проекте есть `src/store/store.js`, где остаются старые mock-данные и вычисления, использовавшиеся на ранних этапах.

На текущем этапе важный практический момент такой:

- часть публичной и административной логики уже переведена на backend API;
- исторические mock-данные в store не являются главным источником истины для реального функционала;
- при дальнейшей чистке системы этот слой можно будет упрощать и вычищать.

То есть frontend уже движется от mock-first подхода к API-first архитектуре.

### 4.7. Как frontend связан с backend

Все данные приходят по HTTP JSON.

Основные паттерны вызова:

- публичные страницы используют `optionalAuthApiRequest`;
- защищенные страницы используют `authorizedApiRequest`;
- все ошибки backend превращаются в нормальный текстовый message в UI;
- в dev-режиме сетевые запросы логируются в консоль.

Для frontend важно, что backend возвращает уже агрегированные данные там, где это имеет смысл.

Пример:

- публичная главная получает season overview одним вызовом;
- страница матча получает и протокол, и составы, и доступных игроков;
- страница игроков получает список отдельно, а popup игрока добирает detail/history отдельными API-вызовами;
- кабинет представителя получает сезоны, состав команды и сезонную заявку из отдельных, но понятных API.

### 5.4. Главные таблицы и их смысл

#### Пользователи и доступ

- `w_user_login` — учетные записи;
- `w_role` — роли;
- `w_user_role` — роли пользователей;
- `w_user_team_scope` — ограничение представителя по команде;
- `w_api_access_rule` — матрица API-level доступа;
- `w_auth_audit_log` — журнал auth событий.

#### Справочники турнира

- `w_team` — команды;
- `w_player` — игроки;
- `w_player_team` — связь игрока с командой;
- `w_media_asset` — логотипы и фото.

#### Сезонная структура

- `w_season` — сезон;
- `w_season_team` — участие команды в сезоне;
- `w_season_player` — участие игрока в сезоне за команду.

#### Турнирное расписание

- `w_tour` — тур;
- `w_tour_match` — матч внутри тура.

#### Реальные матчевые данные

- `w_match_protocol` — итоговое состояние матча;
- `w_match_event` — события матча;
- `w_match_lineup` — заявка команды на матч;
- `w_match_lineup_player` — игроки в матчевой заявке.

### 5.5. Почему `w_season_player` критичен

Это сейчас одна из самых важных таблиц во всей системе.

Она решает архитектурную проблему, которую невозможно нормально решить одним полем в `w_player`.

С ее помощью система может выразить:

- игрок играет в сезоне `Зимний чемп`;
- этот же игрок может играть в сезоне `Тестовый`;
- в одном сезоне он может быть только за одну команду;
- в другом сезоне — уже за другую;
- удаление из сезонной заявки не ломает карточку игрока и не уничтожает историю.

Это и есть правильная база для будущих трансферов.

## 6. Сквозные сценарии работы системы

### 6.1. Публичный пользователь открывает главную

1. Открывает `/`.
2. Frontend запрашивает список сезонов.
3. Frontend выбирает сезон.
4. Frontend вызывает `GET /api/seasons/{seasonId}/overview`.
5. Backend возвращает:
	- сезон;
	- команды сезона;
	- опубликованные туры;
	- матчи внутри туров.
6. Frontend отображает туры и матчи.

### 6.2. Пользователь открывает матч

1. Нажимает на матч.
2. Frontend открывает `/match/{id}`.
3. Вызывает `GET /api/matches/{id}`.
4. Backend возвращает:
	- данные матча;
	- сезон;
	- тур;
	- команды;
	- протокол;
	- события;
	- домашнюю и гостевую заявки.
5. Frontend рендерит полноценную страницу матча.

### 6.3. Администратор создает или меняет сезон

1. Заходит в `/admin`.
2. Работает с формой сезонов.
3. Backend сохраняет сезон и набор команд сезона.
4. Если структура регулярки еще не зафиксирована матчами, backend может пересчитать туры.
5. Если уже есть матчи, backend блокирует опасные изменения структуры.

### 6.4. Администратор работает с туром и матчами

1. Выбирает сезон.
2. Получает туры сезона.
3. Выбирает тур.
4. Получает матчи тура.
5. Создает матч, выбирая только команды этого сезона.
6. При необходимости публикует тур.

### 6.5. Представитель команды работает с заявкой сезона

1. Заходит в `/team-rep-dashboard`.
2. Frontend загружает профиль, сезоны команды и текущий состав.
3. Представитель открывает нужный сезон.
4. Backend возвращает:
	- игроков команды;
	- кто уже выбран в сезон;
	- доступных игроков, свободных в этом сезоне.
5. Представитель:
	- добавляет существующего игрока;
	- или создает нового игрока;
	- или убирает игрока из заявки сезона.
6. Backend валидирует сезонные ограничения.

### 6.6. Подача состава на матч

1. Открывается страница матча.
2. Backend уже знает сезон матча и команды матча.
3. Для каждой команды backend вычисляет `availablePlayers`.
4. В список допускаются только игроки, которые:
	- состоят в команде;
	- присутствуют в `w_season_player` по этому сезону и этой команде.
5. После сохранения обеих заявок статус матча может автоматически измениться.

## 7. Где что хранится и откуда что берется

### 7.1. Источник истины по пользователям

- backend + БД;
- frontend хранит только текущую auth-сессию.

### 7.2. Источник истины по ролям и правам

- таблицы `w_role`, `w_user_role`, `w_api_access_rule`, `w_user_team_scope`;
- backend фильтры и сервисы доступа.

### 7.3. Источник истины по сезонам и структуре турнира

- `w_season`, `w_season_team`, `w_tour`, `w_tour_match`.

### 7.4. Источник истины по игрокам

- карточка игрока — `w_player`;
- связь игрока с командой — `w_player_team`;
- участие игрока в сезоне — `w_season_player`.

### 7.5. Источник истины по матчу

- расписание матча — `w_tour_match`;
- итоговое состояние матча — `w_match_protocol`;
- события матча — `w_match_event`;
- составы на матч — `w_match_lineup`, `w_match_lineup_player`.

## 8. Практические выводы для дальнейшей работы

1. Backend уже стал основным носителем бизнес-логики и дальше эту линию нужно сохранять.
2. Frontend должен продолжать переход от mock-остатков к полностью API-driven работе.
3. Таблица `w_season_player` — центральная точка для всех будущих доработок по заявкам и трансферам.
4. Все новые функции по матчам должны учитывать, что есть три отдельных слоя:
	- расписание;
	- сезонная заявка;
	- фактический состав на матч и протокол.
5. Любой новый модуль трансферов должен не ломать сезонную историю, а опираться на нее.

## 9. Итоговое краткое определение системы

Если описать систему одной формулой, то это:

управляемая backend-логикой турнирная платформа, где frontend является клиентом, а PostgreSQL хранит не только текущие данные, но и историю участия команд и игроков в сезонах, матчах и ролях.

Именно поэтому система уже сейчас готова не только к просмотру статистики, но и к дальнейшему развитию в сторону:

- трансферов;
- более полной аналитики;
- расширенного судейского/протокольного блока;
- полноценного production admin workflow.
